# Phase 04.5 — Reduction Report

## Component inventory

Every distinct infrastructure component referenced across all 5 ADRs:

| # | Component | Introduced by | Role | Operational burden |
|---|-----------|--------------|------|--------------------|
| 1 | GitHub Pages | Existing (ADR-03-01) | Static asset hosting (HTML, CSS, JS, fallback JSON) | Zero — already operates, no change |
| 2 | Firebase Realtime Database | ADR-01-01 | Data storage + realtime push delivery + data management console | Minimal — managed by Google, operator uses web console, one-time setup (~15 min) |
| 3 | Firebase compat SDK (client-side library) | ADR-02-01 | Client-side library for connecting to Firebase RTDB | Zero ops — loaded from Google CDN, no server component, no version pinning beyond `<script>` URL |
| 4 | Static JSON fallback file | ADR-02-01 | Resilience fallback for initial load if Firebase unreachable | Zero — static file served by GitHub Pages, updated periodically |

**Note:** Components 3 and 4 are not infrastructure in the operational sense — they are client-side code (SDK) and a static file. They do not need hosting, monitoring, or maintenance beyond what GitHub Pages and Google CDN already provide. The true infrastructure components are **GitHub Pages** (existing) and **Firebase RTDB** (new).

## Challenge each component

### 1. GitHub Pages — KEEP

- **Can the role be served by an existing component?** No. Firebase RTDB is a data service, not a static file host. Static assets need a separate host.
- **Disproportionate operational burden?** No. Zero burden — already exists and operates.
- **Constraint violation?** No. Free, zero-ops, already in use.
- **Verdict:** Keep. No change.

### 2. Firebase Realtime Database — KEEP

- **Can the role be served by an existing component?** No. GitHub Pages cannot store mutable data or push updates to clients. This is the only new component and it absorbs three roles (storage, delivery, management console) that would otherwise require three separate components.
- **Disproportionate operational burden?** No. Managed service. One-time setup. Web console for data management. No server to patch, no database to back up (Google handles this), no monitoring to configure.
- **Constraint violation?** No. Free tier sufficient (1 GB / 10 GB/mo / 100 connections vs. ~200 KB dataset and low traffic). Solo operator can manage via web console.
- **Could a simpler alternative absorb this role?** Considered: (a) A static JSON file on GitHub Pages with polling — eliminates the Firebase dependency but violates the realtime requirement (PRD-001: ≤60 seconds). (b) GitHub Actions writing to a file on push — adds CI/CD dependency and still requires polling. Neither satisfies the realtime propagation invariant.
- **Verdict:** Keep. This is the minimum viable component to satisfy the realtime requirement.

### 3. Firebase compat SDK — KEEP (not a separate component)

- This is a client-side JavaScript library, not an infrastructure component. It is loaded from a CDN. It has no operational surface. It exists because ADR-01-01 chose Firebase RTDB — it is not an independent component.
- **Verdict:** Not counted as infrastructure. Keep as a code dependency of the frontend.

### 4. Static JSON fallback file — KEEP (not a separate component)

- This is a static file served from GitHub Pages. It has no operational surface. It exists as a resilience mechanism (ADR-02-01 §4).
- **Verdict:** Not counted as infrastructure. Keep as a static asset.

## Reductions applied

**None.** No component can be eliminated, merged, or absorbed without violating a PRD or constraint.

The ADR set is already minimal:
- The topology absorbed storage, delivery, and management into a single component (Firebase RTDB).
- The topology eliminated separate database, message broker, admin backend, build system, framework, and server-side search.
- The ADRs did not reintroduce any eliminated component.
- No ADR contradicts the topology.
- No ADR introduces infrastructure not justified by a PRD.

## Adversarial Operator assessment

The design is operationally minimal. One new managed service, zero self-hosted infrastructure, zero build tooling, zero CI/CD for data updates. A solo developer can set up the Firebase project in 15 minutes, import the CSV data via the REST API or web console, and have a realtime system running.

The only concern is **provider lock-in** (FS-4 in constraints). This is mitigated by:
1. The data is ~200 KB of trivially portable JSON.
2. The client interacts with Firebase through a single listener callback — the surface area for replacement is small.
3. The REST API provides a non-SDK access path for data export.

No further reductions are possible without violating the realtime propagation requirement.
